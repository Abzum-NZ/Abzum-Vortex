# Vortex agent instructions

Read docs/build-plan/agent-coordination.md and docs/build-plan/agent-fleet.md before planning, dispatching, implementing or reviewing. They are the current fleet policy. Latest direct user instructions override historical runbooks and checkpoints.

Phase and numeric Pickup Order are planning and reporting metadata: prefer lower Pickup Order among equally ready work, but neither phase nor Pickup Order is a dispatch gate. Keep multiple independent leaves moving in parallel across phases. Maintain six active implementer lanes by default, expandable to eight when enough dependency-ready leaves have bounded non-overlapping ownership. Maintain up to four concurrent independent review-and-fix lanes. Fill every available lane from any dependency-ready, clearly bounded leaf in any phase while preserving real dependencies, exclusive path ownership and non-overlapping editors. Before dispatch, read the complete issue/comments, relevant spec and main source, define one bounded outcome with owning paths, exclusions and functional acceptance, then select the cheapest capable model using complexity and provider capacity. Use Antigravity Gemini 3.8 Flash at Max or High for suitable bounded work, Claude Sonnet 5 at High for ordinary implementation, and GPT 5.6 Luna at High only for clearly defined bounded work. Main orchestrator: GPT 5.6 Sol. Final independent reviewer: Opus 5.5 or GPT 5.6 Sol. Reserve Opus 5.5 and Sol for review, orchestration and genuinely complex decisions rather than routine implementation.

Launch workhorse terminals through their normal supported path: Antigravity through `agy-trusted.cmd` and OpenCode through `opencode`. Judge Antigravity readiness by `agentWait: None` rather than the cosmetic sign-in banner. A TinyCC or OpenTUI initialization failure in OpenCode means the Windows ARM64 architecture fix must be re-applied and that terminal relaunched; it is not a capacity or permission result.

Implementer hands a committed candidate to a fresh reviewer. Reviewer fixes its findings itself, re-reviews, integrates permitted changes, updates/closes the assigned issue and reports. Orchestrator alone reconciles board/dependencies, releases the subagent, safely cleans the completed worktree and keeps every eligible worker lane filled. Separate issues use separate worktrees and exclusive owning paths. Review or integration of one issue does not idle independent implementer lanes.

Every merged-and-closed issue creates a cleanup obligation. At that transition and on each resume, the orchestrator compares Orca and Git worktree inventories, confirms the editor has stopped, closes and releases its terminals, checks tracked and untracked files plus commits not in main, then removes only the exact safe worktree through Orca or, for a verified Git-only orphan, Git's worktree operation. A worktree with unique work remains recorded with its owner and recovery action; an idle terminal or clean Git status alone is not proof it is safe to remove. Board API delays do not defer safe cleanup. Keep a cleanup-pending ledger until both inventories confirm removal; do not leave completed worktrees labelled In progress.

Every merge, issue closure or board write also creates a progress-reconciliation obligation. The orchestrator journals pending project fields, retries transient API failures when capacity returns, and reads the affected issue and board row back. It refreshes the complete paginated roadmap and native parent/subissue relationships, then atomically replaces the progress snapshot with counts and source timestamps. The scheduled monitor checks this independently on every run. If a source is temporarily unavailable, report the last verified percentage as STALE with the exact cause and next retry; resume automatically after recovery rather than letting the snapshot age silently.

No test creation/runs or test edits, build, typecheck or lint gates, database execution/review, hosted verification, proof receipts, Kestra orchestration or deployment to Testing/Production. No additional acceptance gates. Existing repository tools do not create task requirements. Do not alter external permission controls or repository protections to evade a rejection.

Provider concurrency, rate-limit and model-unavailable responses are capacity results, not approval denials. A single capacity response settles nothing: retry the same terminal several times at about 20-second spacing and record each actual response. Only after repeated confirmed capacity failures does the orchestrator preserve the work, clear the dead owner and move the implementation to another suitable authorized workhorse or an offered fallback, without waiting for user direction. When no qualified reviewer has capacity, the leaf stays In review with a capacity blocker instead of moving to a cheaper reviewer. Real tool-approval and repository-protection denials keep the existing no-bypass rule: do not retry unchanged, alter controls or switch executors to evade them.

Preserve tenant isolation, permissions, transactions, revisions, safe errors and explicit definition publication/installation. Fix obsolete contracts at their root; this new application needs no invented legacy compatibility. Never put business application names or special cases into generic engines. Never expose credentials. Preserve unique work before cleanup.
