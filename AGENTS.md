# Vortex agent instructions

Read docs/build-plan/agent-coordination.md and docs/build-plan/agent-fleet.md before planning, dispatching, implementing or reviewing. They are the current fleet policy. Latest direct user instructions override historical runbooks and checkpoints.

Phase and numeric Pickup Order are planning and reporting metadata: prefer lower Pickup Order among equally ready work, but neither phase nor Pickup Order is a dispatch gate. Keep multiple independent leaves moving in parallel across phases. Maintain eight active implementer lanes by default, expandable to twelve when enough dependency-ready leaves have bounded non-overlapping ownership and provider capacity allows. Review capacity follows the review queue: every handed-off candidate gets an independent reviewer in the same orchestrator cycle, up to six concurrent review-and-fix lanes. Fill every available lane from any dependency-ready, clearly bounded leaf in any phase while preserving real dependencies, exclusive path ownership and non-overlapping editors. Before dispatch, read the complete issue/comments, relevant spec and main source, and shape the issue so it is clear and bounded, splitting it into sub-issues when it exceeds one bounded session (see "Shape before dispatch" in docs/build-plan/agent-coordination.md); define one bounded outcome with owning paths, exclusions and functional acceptance, then select the cheapest capable model using complexity and provider capacity. Primary implementation workhorses are GPT-6 Luna (Codex), OpenCode DeepSeek 4.1 Flash (`deepseek/deepseek-flash`), OpenCode GLM 5.3 Flash and Antigravity Gemini 3.8 Flash at Max or High; Claude Sonnet 5 High is an alternative. Independent reviewers are Claude Opus 5.5 and GPT-6 Sol, always a different session from the implementer. The main orchestrator is one session of Claude Opus 5.5 or GPT-6 Sol. Reserve Opus 5.5 and GPT-6 Sol for review, orchestration and genuinely complex decisions rather than routine implementation. The no-choke-point rules in docs/build-plan/agent-coordination.md apply to every role.

Launch workhorse terminals through their normal supported path: Antigravity through `agy-trusted.cmd` and OpenCode through `opencode`. Judge Antigravity readiness by `agentWait: None` rather than the cosmetic sign-in banner. On this Windows ARM64 host the x64 OpenCode interactive screen crashes at random, so Orca's OpenCode agent command is overridden to `C:\Users\vijay\.orca\bin\opencode-orca-headless.cmd`, which runs every turn on the stable native ARM64 `opencode run` and continues the same session. Launch OpenCode workers normally through Orca; if one returns to the shell prompt without a handoff, first confirm the override is still set in Orca Settings > Agents > OpenCode, then relaunch the preserved leaf once and reassign it if it fails again. Run `C:\Users\vijay\.orca\bin\opencode-fix-arch.cmd` only after an OpenCode upgrade or reinstall, after settling every active OpenCode worker, because it stops all OpenCode processes. A confirmed GLM concurrency-capacity error instead gets same-worker retries at about 20-second spacing, then reassignment to DeepSeek Flash or GPT-6 Luna if it persists. Do not use DeepSeek Pro or retired Herdr tooling.

Implementer hands a committed candidate to a fresh reviewer. The reviewer first reads the complete GitHub issue and every comment, then the linked spec and candidate code. The reviewer fixes its findings itself, re-reviews the final source, integrates permitted changes, updates/closes the assigned issue, writes its own issue's completion fields on the board, and signals the orchestrator with review, merge and closure facts. The orchestrator reconciles shared board state (dependencies, parents, other issues), releases both settled agents, safely cleans the completed worktree and immediately refills available lanes. Separate issues use separate worktrees and exclusive owning paths. Review or integration of one issue does not idle independent implementer lanes.

Every merged-and-closed issue creates a cleanup obligation. At that transition and on each resume, the orchestrator compares Orca and Git worktree inventories, confirms the editor has stopped, closes and releases its terminals, checks tracked and untracked files plus commits not in main, then removes only the exact safe worktree through Orca or, for a verified Git-only orphan, Git's worktree operation. A worktree with unique work remains recorded with its owner and recovery action; an idle terminal or clean Git status alone is not proof it is safe to remove. Board API delays do not defer safe cleanup. Keep a cleanup-pending ledger until both inventories confirm removal; do not leave completed worktrees labelled In progress.

Every merge, issue closure or board write also creates a progress-reconciliation obligation. The orchestrator journals pending project fields, retries transient API failures when capacity returns, and reads the affected issue and board row back. It updates the progress projection from verified event deltas against the last complete roadmap/native-relationship snapshot; one shared complete refresh runs within each reporting interval and after structural changes. The scheduled monitor reads that same snapshot and independently checks source times and deltas instead of repeating the full API fetch. If a source is temporarily unavailable, report the last verified percentage as STALE with the exact cause and next retry; resume automatically after recovery rather than letting the snapshot age silently.

Protect GitHub Project API capacity for live board transitions. The orchestrator owns shared board state and the complete snapshot; implementers and reviewers write only their own assigned issue's row (Status, Current owner, start/finish times) at their own lifecycle transitions, with one targeted mutation and readback using the item and field IDs supplied in their brief; they never run Project scans. Monitors consume the orchestrator's timestamped complete snapshot and targeted readbacks instead of duplicating full Project scans. Persist issue-to-item and field IDs, coalesce all pending changes per issue, skip unchanged fields, batch bounded GraphQL mutations and read back only touched rows. Write current Status and owner first, then other changed metadata and parent rollups. Refresh all Project pages and native relationships once per scheduled snapshot cycle or structural roadmap change, using the same result for board audit and progress. Check actual GraphQL response headers and errors, not the cached REST rate-limit projection; reserve capacity for new transitions, retry pending writes at reset and never repeatedly run a full scan against an exhausted bucket.

No test creation/runs or test edits, build, typecheck or lint gates, database execution/review, hosted verification, proof receipts, Kestra orchestration or deployment to Testing/Production. No additional acceptance gates. Existing repository tools do not create task requirements. Do not alter external permission controls or repository protections to evade a rejection.

Provider concurrency, rate-limit and model-unavailable responses are capacity results, not approval denials. A single capacity response settles nothing: retry the same terminal several times at about 20-second spacing and record each actual response. Only after repeated confirmed capacity failures does the orchestrator preserve the work, clear the dead owner and move the implementation to another suitable authorized workhorse or an offered fallback, without waiting for user direction. When no qualified reviewer has capacity, the leaf stays In review with a capacity blocker instead of moving to a cheaper reviewer. Real tool-approval and repository-protection denials keep the existing no-bypass rule: do not retry unchanged, alter controls or switch executors to evade them.

Preserve tenant isolation, permissions, transactions, revisions, safe errors and explicit definition publication/installation. Fix obsolete contracts at their root; this new application needs no invented legacy compatibility. Never put business application names or special cases into generic engines. Never expose credentials. Preserve unique work before cleanup.
