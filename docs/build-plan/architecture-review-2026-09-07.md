# Whole-platform architecture review — 7 September 2026

[Specification](../specification/README.md) · [Build plan](README.md) · [Flow delivery map](frontend-rule-designer.md)

## Outcome

Keep the existing generic service architecture. Extend the shared Frontend Rule Designer for configurable component data, sequential protected actions, managed flows and node execution identities. Reuse Access for authority, Query for reads, owning operations for writes, Definition for publication, Page Designer for forms and Kestra for durable work. Do not create another permission engine, designer, execution service package or frontend durable scheduler.

The review found a real missing prerequisite: [#322](https://github.com/Abzum-NZ/Abzum-Vortex/issues/322) provides scoped node execution identities. Existing [#104](https://github.com/Abzum-NZ/Abzum-Vortex/issues/104) resolves external callers and [#40](https://github.com/Abzum-NZ/Abzum-Vortex/issues/40) manages access; neither grants permission to execute a flow node as another account. This is an engineering dependency, not an unresolved product decision.

## Findings and resolutions

The Supabase guidance check retains the distinction between database grants and row policies, private function exposure and scoped application authority. In particular, a System node must not become a service-role bypass, and a query/view must not evade viewer restrictions. These boundaries match the official [row-security guide](https://supabase.com/docs/guides/database/postgres/row-level-security) and [API security guide](https://supabase.com/docs/guides/api/securing-your-api). This documentation check is not an advisor run or verification of a hosted database.

| Finding                                                                       | Resolution and owner                                                                                                                                                                                                                                                                                                                                                                                                                      |
| ----------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A blanket read-only loading rule conflicts with configurable flows.           | Component flows may read, transform, write, requery and return results. Semantic events—not renders/prefetch—start them. [#58](https://github.com/Abzum-NZ/Abzum-Vortex/issues/58), [#67](https://github.com/Abzum-NZ/Abzum-Vortex/issues/67).                                                                                                                                                                                            |
| A universal single final commit prevents configured multi-step actions.       | Each owning operation remains atomic. Multiple explicit commits are allowed; later cancellation/failure preserves confirmed changes. Collect-first remains an optional atomic pattern. [#47](https://github.com/Abzum-NZ/Abzum-Vortex/issues/47), [#50](https://github.com/Abzum-NZ/Abzum-Vortex/issues/50), [#58](https://github.com/Abzum-NZ/Abzum-Vortex/issues/58), [#68](https://github.com/Abzum-NZ/Abzum-Vortex/issues/68).        |
| Node actor selection lacks a trusted execution grant.                         | Add private revisioned scope and current resolution in existing Access through [#322](https://github.com/Abzum-NZ/Abzum-Vortex/issues/322); descriptions/configuration cannot grant authority. No borrowed role-management delegation.                                                                                                                                                                                                    |
| Running with more authority can accidentally disclose data.                   | Keep privileged intermediate values server-only. Enforce invoking-viewer visibility for returned/derived values, counts, errors, logs, files, MCP and writes; no implicit declassification. [#322](https://github.com/Abzum-NZ/Abzum-Vortex/issues/322), [#54](https://github.com/Abzum-NZ/Abzum-Vortex/issues/54), [#58](https://github.com/Abzum-NZ/Abzum-Vortex/issues/58), [#67](https://github.com/Abzum-NZ/Abzum-Vortex/issues/67). |
| Module-exposed queries and private managed flows are not existing contracts.  | Explicit versioned source/canonical/compiler/reference/publication/restore work, with exact dependencies and public projections. [#54](https://github.com/Abzum-NZ/Abzum-Vortex/issues/54), [#250](https://github.com/Abzum-NZ/Abzum-Vortex/issues/250), [#58](https://github.com/Abzum-NZ/Abzum-Vortex/issues/58), [#73](https://github.com/Abzum-NZ/Abzum-Vortex/issues/73).                                                            |
| A query transform can invalidate paging or record identity.                   | Query owns dataset-wide filters, sorting, totals and cursors; transforms operate on bounded returned data and cannot fabricate writable source identities or widened authority. [#54](https://github.com/Abzum-NZ/Abzum-Vortex/issues/54), [#67](https://github.com/Abzum-NZ/Abzum-Vortex/issues/67).                                                                                                                                     |
| Load retries and write invalidation can repeat business effects.              | Use semantic invocation/cause and the per-operation duplicate receipts planned in the owning tasks. Suppress self-caused changing-flow loops; reconcile an uncertain operation before continuing. No whole-graph replay with new branch decisions. [#58](https://github.com/Abzum-NZ/Abzum-Vortex/issues/58), [#67](https://github.com/Abzum-NZ/Abzum-Vortex/issues/67).                                                                  |
| Cancellation and durable starts could be reported as rolled back incorrectly. | Record exact committed/partial/uncertain/pending outcomes. A durable intent commits at its configured node and survives later UI failure. [#68](https://github.com/Abzum-NZ/Abzum-Vortex/issues/68), [#77](https://github.com/Abzum-NZ/Abzum-Vortex/issues/77).                                                                                                                                                                           |
| Activity could grow another parallel history model.                           | Keep operation Activity under the effective actor; link an initiating account's content-free use entry when present. System-started work records the real system actor/cause, not a fabricated human. [#322](https://github.com/Abzum-NZ/Abzum-Vortex/issues/322), [#115](https://github.com/Abzum-NZ/Abzum-Vortex/issues/115) consume completed [#252](https://github.com/Abzum-NZ/Abzum-Vortex/issues/252).                             |
| Public callers have no current organisation account.                          | Only explicitly public protected operations with separately authorised scoped System bindings; no anonymous user nomination. [#107](https://github.com/Abzum-NZ/Abzum-Vortex/issues/107).                                                                                                                                                                                                                                                 |
| Installation/copy could accidentally transfer privilege.                      | Copy definitions and permitted configuration, never live grants or private managed source. Bind grants to exact releases; upgrades cannot silently broaden them. [#64](https://github.com/Abzum-NZ/Abzum-Vortex/issues/64), [#73](https://github.com/Abzum-NZ/Abzum-Vortex/issues/73), [#112](https://github.com/Abzum-NZ/Abzum-Vortex/issues/112).                                                                                       |
| New engine dependencies could cycle back into early contracts.                | [#250](https://github.com/Abzum-NZ/Abzum-Vortex/issues/250) defines descriptors first; [#54](https://github.com/Abzum-NZ/Abzum-Vortex/issues/54) and [#322](https://github.com/Abzum-NZ/Abzum-Vortex/issues/322) consume them; [#58](https://github.com/Abzum-NZ/Abzum-Vortex/issues/58) consumes all three. No reverse dependencies on designer UI.                                                                                      |
| Security work could drift into infrastructure or elaborate generic recovery.  | Reuse current transactions, revisions and Access version, plus the receipts/private drafts planned in owning tasks rather than another store. Keep durable unattended work in Kestra; upgrades/backups and unrelated infrastructure remain outside this change.                                                                                                                                                                           |

## Delivery order and review limits

### Runtime placement correction

The source review also makes the planned flow implementation location explicit: shared Rule (tier 1) stays a pure graph transition/interpreter returning typed intents/outcomes. The headless server coordinator belongs to existing App (tier 8) under [#58](https://github.com/Abzum-NZ/Abzum-Vortex/issues/58), using lower-tier public Query/Record/Access/Workflow APIs. Record calls Rule's transaction-safe subset, never App. Page (tier 9)/web renders typed presentation/form intents through [#68](https://github.com/Abzum-NZ/Abzum-Vortex/issues/68) and validates protected continuation evidence; App must not import Page or disguise an upward dependency through callbacks. This closes a potential implementation-level tier inversion without a new package or weakened boundary checks. [#64](https://github.com/Abzum-NZ/Abzum-Vortex/issues/64) remains a later UI/installation consumer.

Current Phase 3 priorities remain record visibility [#36](https://github.com/Abzum-NZ/Abzum-Vortex/issues/36) and access administration [#40](https://github.com/Abzum-NZ/Abzum-Vortex/issues/40), followed by their dependent consistent data-access enforcement [#35](https://github.com/Abzum-NZ/Abzum-Vortex/issues/35). The designer work follows the [actual prerequisites](frontend-rule-designer.md#dependency-order), not a UI-first jump. No business decision remains open from this review.

Implementation reviewers must check the final code against its entire updated issue: permissions, tenant isolation, concurrency, genericness and complexity. This document does not approve unrelated uncommitted code or close implementation issues. The final documentation/task review and live graph verification are recorded with this change's delivery evidence.
