# Local preview browser adapter

`tooling/fleet/local-preview-browser.mjs` is the browser-only adapter for the Codex-owned local preview runner in issue #1702. The runner prepares the candidate checkout, server, database, and declared fixture fingerprints. This adapter independently checks the candidate `HEAD`, validates the supplied origin, nonce, and fixture-map shape, then owns one headless Edge instance for the sign-in, Companies list, New company, and save steps.

The browser automation uses Node 24 built-ins. On Windows, cleanup also uses a bounded read-only PowerShell/CIM process probe because Edge can relaunch outside the initially spawned process. The probe excludes only the validated PID-0 `System Idle Process` pseudo-record; malformed or unexpected real process records fail closed. It starts the pinned executable `C:/Program Files (x86)/Microsoft/Edge/Application/msedge.exe` with a new private profile, loopback-only DevTools address, port `0`, and the Edge compatibility-relaunch skip flag. It identifies one ownership root by its exact executable, private-profile argument, creation time and parent. Because a live launcher can have profile-matching Edge children, the chosen root must uniquely cover every process using the private profile through a creation-checked descendant chain; zero or multiple covering roots fail closed. The adapter then checks that the DevTools browser endpoint from its `DevToolsActivePort` file matches. It connects only to the uniquely launched `about:blank` page. It never attaches to an existing browser or prints credentials, page text, raw process command lines, environment values, or the profile path.

The runner passes no credential arguments and provides these environment variables:

- `VORTEX_PREVIEW_BASE_URL`: an HTTP origin on `127.0.0.1` or `::1`, with an explicit port and no path, query, or fragment.
- `VORTEX_PREVIEW_HEAD_SHA`: the full 40-character candidate SHA; it must equal `git rev-parse --verify HEAD` in the prepared checkout.
- `VORTEX_PREVIEW_RUN_NONCE`: a nonempty, bounded ASCII invocation nonce.
- `VORTEX_PREVIEW_FIXTURE_FINGERPRINTS`: a JSON object mapping safe relative fixture paths to 64-character SHA-256 fingerprints. The adapter validates every entry and independently hashes every provided regular file within the prepared checkout before launch, then echoes the exact validated map. It accepts additional prepared fixtures without assigning them hard-coded roles. The runner owns checkout-to-server identity and fixture preparation.

The prepared fixture must expose the exact `Local test sign-in (development only)` button. The Companies list action, form fields, and Save action must each have one visible, enabled match for their exact accessible name. The required Company type is explicitly set to the `Customer` option; there is no fallback to the first input or checkbox. The generated company name includes the run nonce and a fresh UUID, and success requires that exact name on a CRM company detail route.

Readiness, DevTools commands, navigation, individual steps, and the overall invocation have fixed deadlines. The main frame must stay at the declared preview origin. Browser requests may use explicit loopback hosts, including the separate local Supabase port used by sign-in; an observed request to a remote host prevents PASS. A second control match, unavailable required control, missing or malformed DevTools state, candidate SHA mismatch, timeout, failed save, or uncertain browser exit also fails closed. Every JSON result, including a failure, contains `browser_cleanup: {"confirmed": boolean}`. The result contains only safe reason codes and steps actually completed. PASS requires all four checks and `browser_cleanup.confirmed === true`; exit status is `0` only for PASS. `--help` is side-effect free and is not browser evidence.

The smoke result also carries one safe `action_stage` enum from `not_started` through `complete`; it records the stage at failure without page text, URLs or credentials. After clicking New company, the adapter waits for the CRM definition's `crm_company_create` route before locating the form. It then distinguishes waiting for the Company name control from waiting for the Customer option. A failed route, missing form or unavailable option remains FAIL; the stage does not weaken any control or cleanup check.

Only a failure at `customer_control` may carry `customer_control_probe`. This best-effort read repeats the exact form and Company type group lookup at failure time and reports eight counts, each capped at 1024, plus `capped` and `scope_valid` booleans. The counts detect loss of the matching form/group scope and distinguish checkbox candidates, visible candidates, exact Customer names, disabled exact matches and visible Customer labels. Because the matching form lookup itself requires the Company type group, `form_count:0` cannot distinguish a missing form from a missing or renamed group. When the form or group is not unique, `scope_valid` is false and all group-scoped counts are zero and must be ignored. If the probe cannot run, the field is absent; it never replaces the original failure or affects cleanup. No text, markup, field value, URL or credential is recorded.

When that failure probe confirms one form and Company type group, a second best-effort `customer_visibility_probe` reads only the exact Customer semantic checkbox root associated with its visible label. It reports a bounded root count and, only when the root is unique, booleans for the same hidden, ARIA, computed display, visibility, opacity and rectangle conditions used by the adapter's visibility check. It also reports whether the root computes to inline display, carries the expected checkbox class, or has its own inline style. No computed CSS value, geometry, label text, markup or identifier leaves the page. Missing or ambiguous roots have null condition flags. This diagnostic cannot alter the original failure, acceptance or browser cleanup.

On shutdown the adapter requests `Browser.close`, then requires two read-only snapshots confirming the actual browser root, known descendants, any process with the exact private profile, and the original launcher have exited. Only then does it remove the verified profile directory created by this invocation and confirm removal. An initial launcher exit alone is never cleanup proof. If process identity, exit or profile removal is uncertain, `browser_cleanup.confirmed` is false, the result is FAIL, and the profile is preserved for the owner. The adapter does not issue a broad process kill or delete an unverified path. The runner must retain exclusive preview ownership when this attestation is missing or false, even if the adapter itself exits.

When browser startup or an application step fails before cleanup, `reason` retains that first safe failure code. A later cleanup failure is reported by `browser_cleanup.confirmed === false`; it does not erase the original reason. The runner treats cleanup uncertainty as a lock-retention condition regardless of the primary failure.

Implementation validation is source-only. `node --check` and `--help` do not run Edge, start the preview server, access the database, or prove browser acceptance. A real run requires independent review and the lead's explicit preview ownership grant on the exact candidate SHA.

For a lead-approved browser lifecycle diagnostic, first pin and verify the reviewed adapter SHA-256, then run `node tooling/fleet/local-preview-browser.mjs --browser-lifecycle-probe` from its reviewed checkout. This mode needs no preview environment variables, server, fixture, or database. It opens only its unique `about:blank` page, uses the same Edge launch, DevTools identity, and cleanup code as the smoke adapter, and emits `vortex.local-preview.browser-lifecycle.v1` JSON. The safe `startup_phase`, launch and ownership booleans, root-candidate and covering-root counts, primary `reason` if any, and `browser_cleanup.confirmed` distinguish startup from cleanup without exposing the profile, browser endpoint, command line, or credentials. `LIFECYCLE_CONFIRMED` with exit `0` means only that the browser lifecycle completed; it contains no product checks and cannot satisfy the runner's smoke evidence schema. An uncertain exit retains the private profile and requires owner recovery before another launch.
