# Local preview browser adapter

`tooling/fleet/local-preview-browser.mjs` is the browser-only adapter for the Codex-owned local preview runner in issue #1702. The runner prepares the candidate checkout, server, database, and declared fixture fingerprints. This adapter independently checks the candidate `HEAD`, validates the supplied origin, nonce, and fixture-map shape, then owns one headless Edge instance for the sign-in, Companies list, New company, save, and definition-backed Service Desk comparison steps. The four original smoke checks retain their original meaning; the added theme checks are additional requirements for PASS.

The browser automation uses Node 24 built-ins. On Windows, cleanup also uses a bounded read-only PowerShell/CIM process probe because Edge can relaunch outside the initially spawned process. The probe excludes only the validated PID-0 `System Idle Process` pseudo-record; malformed or unexpected real process records fail closed. It starts the pinned executable `C:/Program Files (x86)/Microsoft/Edge/Application/msedge.exe` with a new private profile, loopback-only DevTools address, port `0`, and the Edge compatibility-relaunch skip flag. It identifies one ownership root by its exact executable, private-profile argument, creation time and parent. Because a live launcher can have profile-matching Edge children, the chosen root must uniquely cover every process using the private profile through a creation-checked descendant chain; zero or multiple covering roots fail closed. The adapter then checks that the DevTools browser endpoint from its `DevToolsActivePort` file matches. It connects only to the uniquely launched `about:blank` page. It never attaches to an existing browser or prints credentials, page text, raw process command lines, environment values, or the profile path.

The runner passes no credential arguments and provides these environment variables:

- `VORTEX_PREVIEW_BASE_URL`: an HTTP origin on `127.0.0.1` or `::1`, with an explicit port and no path, query, or fragment.
- `VORTEX_PREVIEW_HEAD_SHA`: the full 40-character candidate SHA; it must equal `git rev-parse --verify HEAD` in the prepared checkout.
- `VORTEX_PREVIEW_RUN_NONCE`: a nonempty, bounded ASCII invocation nonce.
- `VORTEX_PREVIEW_FIXTURE_FINGERPRINTS`: a JSON object mapping safe relative fixture paths to 64-character SHA-256 fingerprints. The adapter validates every entry and independently hashes every provided regular file within the prepared checkout before launch, then echoes the exact validated map. It accepts additional prepared fixtures without assigning them hard-coded roles. The runner owns checkout-to-server identity and fixture preparation.
- `VORTEX_PREVIEW_SCREENSHOT_OUTPUT` and `VORTEX_PREVIEW_SCREENSHOT_STATE_DIR`: set together only for the explicit `diagnose-existing --screenshot-output` opt-in. Both must be absolute; the output must be a new conservative PNG basename directly inside the private state directory. The runner owns outside-worktree validation and enforces mode `0700` on POSIX; on Windows the operator must choose a private directory with an appropriate inherited ACL. The adapter rejects dot segments, reparse/symlink components, an existing output, or a changed path before capture and again before exclusive file creation. These variables are absent for ordinary `run`, preflight and default diagnostic operation.

The prepared fixture must expose the exact `Local test sign-in (development only)` button. The Companies list action, form fields, and Save action must each have one visible, enabled match for their exact accessible name. The required Company type is explicitly set to the `Customer` option; there is no fallback to the first input or checkbox. The generated company name includes the run nonce and a fresh UUID, and success requires that exact name on a CRM company detail route.

Readiness, DevTools commands, navigation, individual steps, and the overall invocation have fixed deadlines. The main frame must stay at the declared preview origin. Browser requests may use explicit loopback hosts, including the separate local Supabase port used by sign-in; an observed request to a remote host prevents PASS. A second control match, unavailable required control, missing or malformed DevTools state, candidate SHA mismatch, timeout, failed save, or uncertain browser exit also fails closed. Every JSON result, including a failure, contains `browser_cleanup: {"confirmed": boolean}`. The result contains only safe reason codes, fixed booleans and bounded numeric metrics; it never includes page text, markup, URLs, DOM identifiers, colors, CSS values, credentials or profile paths. PASS requires all four original checks, all nine theme checks, all ten positive theme metrics in range, and `browser_cleanup.confirmed === true`; when screenshot capture is requested, that capture must succeed too. Exit status is `0` only for PASS. `--help` is side-effect free and is not browser evidence.

The result also carries one safe `action_stage` enum from `not_started` through `complete`; it records the stage at failure without page text, URLs or credentials. The theme stages are `maia_root`, `maia_active_menu`, `maia_table`, `secondary_button`, `customer_dimensions`, `primary_rest`, `primary_hover` and `default_style_comparison`; the optional screenshot has its own `companies_screenshot` stage. Existing stages, including `save_confirmation`, remain. After clicking New company, the adapter waits for the CRM definition's `crm_company_create` route before locating the form. It then distinguishes waiting for the Company name control from waiting for the Customer option. A failed route, missing form or unavailable option remains FAIL; the stage does not weaken any control or cleanup check. `complete` is emitted only after every browser and theme check passes and browser cleanup is confirmed. Screenshot failures use only the safe reasons `companies_row_unavailable` and `screenshot_artifact_failed`; no filesystem path or basename is returned.

## Bounded theme evidence

On the initial CRM Companies route, the adapter requires one Maia/default/bold style root with a rendered theme and exactly one visible sidebar. In that sidebar it requires one visible current-page `a[data-slot=sidebar-menu-button]` with the exact same-origin Companies destination, accessible name `Companies`, and active state. It compares that link's computed background with a same-sidebar `--sidebar-accent` sentinel and requires positive active-menu and resolved base radii. It also requires a unique New company control declared secondary whose computed background matches a same-root `--vortex-secondary` sentinel. Published navigation item IDs are resolved UUIDs, so the adapter does not match authored ID aliases.

After the exact generated company is confirmed on its detail page, the adapter returns once to the CRM Companies route. It waits for the exact generated name in the corresponding `table-cell` under the unique visible `Company name` header, then requires one rendered table with a visible non-checkbox header whose inline padding matches a same-root `calc(var(--spacing, 0.25rem) * 3)` sentinel and whose header row has a positive solid bottom border. A temporarily empty table result retries within the existing 30-second row wait; multiple tables, ambiguous scopes or duplicate/ambiguous headers or rows fail immediately. This saved-row and table verification is required on every flow and cannot be skipped because the initial list is empty. If screenshot capture is requested, it uses this same Companies visit before the Service Desk comparison.

The Customer evidence is measured on the exact CRM create route. It requires one semantic `[role=checkbox][data-slot=checkbox]` named Customer, associated with the visible Customer label in the unique Company type group. The result records its computed width and height plus rendered rectangle width and height. Each reported theme metric is finite, positive, and at most 256 pixels.

Before saving, the unique visible enabled form-scoped Save control must declare the primary variant, which the registered control maps to the shared default Button. The adapter first scrolls it into view and moves the pointer away, so its rest measurement cannot inherit the prior pointer position. Its computed fill and visible foreground must equal same-root browser-resolved `--primary` and `--primary-foreground` sentinels. Its positive-width border must match Maia's transparent border. The adapter records that rest fill and the same button node, moves the real CDP mouse to its viewport center, then waits up to two seconds for `:hover` and a changed fill matching a same-root `color-mix(in oklab, var(--primary) 80%, transparent)` sentinel, as Maia's published `hover:bg-primary/80` specifies. The foreground must still match its resolved primary foreground. It then moves the pointer to the viewport corner and verifies that Save is no longer hovered before the existing click. Transient button state is removed before the click. A missing or mismatched observation remains FAIL; no legacy inset-shadow behavior is required.

After the saved-row/table verification, and optional screenshot capture, the same owned browser navigates to `/abzum/abzum/vortex.app.service_desk/service_desk_overview`. It requires one Nova/default/subtle root, exactly one visible sidebar, and one visible active current-page link with that exact same-origin destination and accessible name `Overview`. Same-scope sentinels resolve the base radius and primary fill; a same-sidebar sentinel resolves the accent. The comparison requires Maia's base radius to exceed Nova's and the rendered active-menu radii to differ. Browser-resolved primary fills and active-menu backgrounds must each differ between the applications. Temporary sentinels are removed in `finally`. The comparison colors are held only in same-origin session storage for this invocation, removed during comparison or best-effort failure cleanup, and never returned in adapter output. Verified private-profile removal remains the final cleanup boundary.

The fixed result adds booleans `maia_root`, `maia_active_menu`, `maia_table`, `secondary_button`, `customer_dimensions`, `primary_rest`, `primary_hover`, `large_radius`, and `default_style_distinct`. Its `theme_metrics` object contains only `customer_computed_width_px`, `customer_computed_height_px`, `customer_rect_width_px`, `customer_rect_height_px`, `maia_table_header_padding_px`, `maia_table_border_px`, `maia_base_radius_px`, `maia_menu_radius_px`, `nova_base_radius_px`, and `nova_menu_radius_px`. Metrics are added only after they are actually measured; a failed result can carry a partial object. PASS requires all nine booleans true and all ten metrics present, finite, positive and within range. The only new reason code is `theme_check_failed`.

For a `theme_check_failed` at `action_stage: "maia_active_menu"`, the adapter can add the optional top-level `maia_active_menu_failed_predicate` enum. Its only values are `wrong_route`, `root_count`, `root_theme`, `nav_item_count`, `current_link_count`, `link_not_visible`, `inactive_link`, `sidebar_scope`, `sentinel_resolution`, `menu_radius`, `base_radius`, `menu_background`, and `comparison_state`. The adapter records the first failed predicate before the existing metric and check validation fails. The field contains no page or style values and never affects any check, metric, PASS condition, or cleanup requirement. The runner projects it only after validating result identity, schema, checks, reason, and cleanup shape; its `maia_active_menu_failed_predicate_valid` flag is true only when the result is FAIL at that exact stage with `theme_check_failed` and the enum is recognized. Missing, malformed, or out-of-context evidence is omitted and marked invalid. If the page evaluation itself fails before returning a predicate, the field is absent.

The same bounded `maia_active_menu` evaluation may add optional `maia_foreground_probe` evidence after the unique visible current Companies link is established. It contains exactly eight booleans: `root_primary_foreground_present`, `sidebar_primary_foreground_present`, `sidebar_accent_foreground_present`, `anchor_accent_foreground_present`, `anchor_matches_accent_foreground`, `label_matches_anchor`, `accent_matches_primary_foreground`, and `sidebar_dark_scheme_resolved`. The probe compares only fixed computed-style and same-sidebar sentinel conditions; each sentinel explicitly inherits `color-scheme` and is removed in `finally`. The direct label span must be unique and visible. Any probe evaluation or scope failure omits the optional object without changing the existing menu evaluation, failure reason, check, metric, or cleanup behavior. No CSS values, colors, DOM text, HTML, URL, coordinates, or credentials are returned. The runner projects only the exact key set with boolean values after identity, schema, checks, reason, and cleanup shape are valid; missing or malformed evidence is represented only by `maia_foreground_probe_valid: false`. These observations are diagnostic only and never contribute to PASS.

## Optional Companies screenshot

Only an explicit `diagnose-existing --screenshot-output` request enables capture; all existing defaults remain unchanged. The required post-save return to CRM Companies, exact generated-row readiness and table check run whether or not screenshot capture is enabled. With capture enabled, the adapter revalidates the pinned local origin, path and unique Maia style root and rechecks the unique visible `Company name` header in the table's `table-head` slots and unique corresponding `table-cell` text match during the same Companies visit. It never returns that text, row markup, selectors, URL or DOM identifier. The row is scrolled into the viewport and must have a positive on-screen rectangle. A zero-table/loading state retries only within the existing bounded wait; multiple tables, ambiguity, or an absent/hidden/out-of-page exact row fail with `companies_row_unavailable`. The list sorts names and paginates 50 rows; if the generated row is not on the rendered page, the adapter fails closed rather than changing pagination, capturing another row or weakening the assertion. Screenshot mode does not navigate to Companies a second time.

The same owned CDP browser captures the viewport as PNG only after those checks. It verifies the PNG signature, IHDR shape, dimensions up to 8192 by 8192 and decoded size at most 8 MiB. It rechecks origin, exact path and Maia root after capture, then creates the exact requested file with exclusive-create semantics; an existing path is never overwritten and a partial file is never automatically removed. The adapter emits only `screenshot: {"sha256":"<64 lowercase hex>","bytes":<bounded integer>}`. The runner independently revalidates the file after the adapter and browser cleanup, including regular-file/no-reparse identity, PNG IHDR CRC, dimensions, size and SHA-256. An invalid or missing requested artifact fails the diagnostic. The screenshot path, basename, PNG contents and company name do not enter adapter JSON, structured runner evidence, stdout or stderr. No screenshot is taken during sign-in or credential handling. The diagnostic remains `product_preview_pass:false`; a human still needs to inspect the saved image before treating the visual review as accepted.

Only a failure at `customer_control` may carry `customer_control_probe`. This best-effort read repeats the exact form and Company type group lookup at failure time and reports eight counts, each capped at 1024, plus `capped` and `scope_valid` booleans. The counts detect loss of the matching form/group scope and distinguish checkbox candidates, visible candidates, exact Customer names, disabled exact matches and visible Customer labels. Because the matching form lookup itself requires the Company type group, `form_count:0` cannot distinguish a missing form from a missing or renamed group. When the form or group is not unique, `scope_valid` is false and all group-scoped counts are zero and must be ignored. If the probe cannot run, the field is absent; it never replaces the original failure or affects cleanup. No text, markup, field value, URL or credential is recorded.

When that failure probe confirms one form and Company type group, a second best-effort `customer_visibility_probe` reads only the exact Customer semantic checkbox root associated with its visible label. It reports a bounded root count and, only when the root is unique, booleans for the same hidden, ARIA, computed display, visibility, opacity and rectangle conditions used by the adapter's visibility check. It also reports whether the root computes to inline display, carries the expected checkbox class, or has its own inline style. No computed CSS value, geometry, label text, markup or identifier leaves the page. Missing or ambiguous roots have null condition flags. This diagnostic cannot alter the original failure, acceptance or browser cleanup.

On shutdown the adapter requests `Browser.close`, then requires two read-only snapshots confirming the actual browser root, known descendants, any process with the exact private profile, and the original launcher have exited. Only then does it remove the verified profile directory created by this invocation and confirm removal. An initial launcher exit alone is never cleanup proof. If process identity, exit or profile removal is uncertain, `browser_cleanup.confirmed` is false, the result is FAIL, and the profile is preserved for the owner. The adapter does not issue a broad process kill or delete an unverified path. If this attestation is missing or false, the runner leaves the browser operation unresolved and keeps the preview lease fenced, even if the adapter process exits. A failed browser result likewise leaves that external operation unresolved and retains the lease for named operator recovery, even with positive cleanup attestation; cleanup alone cannot authorize release. Lease expiry or a free web port is not proof that browser descendants or an external operation are complete.

When browser startup or an application step fails before cleanup, `reason` retains that first safe failure code. A later cleanup failure is reported by `browser_cleanup.confirmed === false`; it does not erase the original reason. The runner treats cleanup uncertainty as a lease-fence and operator-recovery condition regardless of the primary failure. Only verified owner/process cleanup and resolved external-operation state permit release.

On Windows, the outer runner supervisor enforces its two-hour owner deadline outside the runner loop and contains the owner in a kill-on-close Job Object. If the deadline expires, the runner records operator recovery state and retains the lease even after contained processes stop; process identity, process accounting, port evidence and pending external-operation history require owner review. This source integration does not establish operating-runtime acceptance: nested Job Object compatibility and deadline recovery remain NOT_RUN, and preview remains unavailable pending separate controlled acceptance.

Implementation validation is source-only. `node --check` parses the outer module but not the browser page expressions assembled from template strings. Source review also syntax-parses each generated theme and screenshot-row expression in memory with `node:vm.Script`, using a stub `devtools.evaluate` that never executes the expression or contacts a page. This catches duplicate lexical declarations in generated code. `--help` is side-effect free; none of these checks run Edge, start the preview server, access the database, or prove browser acceptance. A real run requires independent review and the lead's explicit preview ownership grant on the exact candidate SHA.

For a lead-approved browser lifecycle diagnostic, first pin and verify the reviewed adapter SHA-256, then run `node tooling/fleet/local-preview-browser.mjs --browser-lifecycle-probe` from its reviewed checkout. This mode needs no preview environment variables, server, fixture, or database. It opens only its unique `about:blank` page, uses the same Edge launch, DevTools identity, and cleanup code as the smoke adapter, and emits `vortex.local-preview.browser-lifecycle.v1` JSON. The safe `startup_phase`, launch and ownership booleans, root-candidate and covering-root counts, primary `reason` if any, and `browser_cleanup.confirmed` distinguish startup from cleanup without exposing the profile, browser endpoint, command line, or credentials. `LIFECYCLE_CONFIRMED` with exit `0` means only that the browser lifecycle completed; it contains no product checks and cannot satisfy the runner's smoke evidence schema. An uncertain exit retains the private profile and requires owner recovery before another launch.
