Vortex · Fleet operating policy · 22 September 2026

One ordered phase.
Several bounded tasks.

GPT 5.6 Sol coordinates a parallel current-phase wave. Independent workhorse agents build bounded leaves in separate worktrees. Opus 5 or Sol reviewers fix their own findings, re-review and close integrated work while the orchestrator keeps other eligible lanes moving.

This page explains the process. It is not a live status dashboard.

Strict phase order with parallel leaves. Work only in the earliest incomplete phase. Scan leaves by Pickup Order and keep six independent implementer lanes filled by default, expanding to eight when bounded non-overlapping work is eligible. Run up to four independent Opus 5/Sol review-and-fix lanes. A blocked or active lower pickup remains visible but does not idle higher independent leaves in the same phase. Never renumber silently or start a later phase early.

The issue lifecycle

  1. Main orchestrator · GPT 5.6 Sol High

    Build the current-phase work wave

    Backlog → Ready

    Read the complete issue and comments, current spec, native dependencies and main source for each candidate. Identify what already exists and exactly what remains. Confirm outcome, owning paths, exclusions and code-review acceptance before assigning an agent.

    Pickup rules

    Read every roadmap page; ignore parent/phase rollups as dispatch targets. Scan the earliest incomplete phase in Pickup Order and select every dependency-ready leaf with non-overlapping ownership until the worker lanes are full. Missing or duplicate numbers, cycles or forward dependencies require an explicit ordering correction. Do not remove real blockers to manufacture readiness or enter a later phase early.

  2. Main orchestrator → workhorse fleet

    Assign bounded independent implementations

    Ready → In progress after actual start

    Match complexity to model and current usage. Prefer GLM, Gemini Flash, Sonnet and Terra for implementation, and spread qualified work across providers. Record actual agent, estimate, branch, worktree and dispatch. Use one isolated issue worktree per leaf. A planned assignment or accepted input is not a started worker.

  3. Implementer → main orchestrator

    Build and hand off the candidate

    In progress → In review

    Commit and push the bounded change. Report functionality, candidate commit, acceptance mapping and limitations. Stop editing. The orchestrator settles/releases the implementer and gives a fresh reviewer exclusive ownership of the same worktree.

  4. Independent reviewer · Opus 5 or GPT 5.6 Sol High

    Review → fix findings → re-review

    In review

    Inspect the full diff and affected callers against the issue and spec. Fix findings directly, commit corrections and inspect the final candidate again. Repeat inside this review session. Do not send ordinary fixes back to the implementer.

  5. Same reviewer

    Integrate, update and close the issue

    Reviewed source merged → issue completed

    Open the candidate PR if absent. Integrate the reviewed PR into main through permitted repository operations. Re-review conflict-resolution changes. Confirm merge, update the assigned issue with the implemented outcome and final review, and close it completed. An open PR is not Done.

    Reviewer completion message
    Issue / phase / pickup; PR; reviewed commit; merge commit; functionality built; findings fixed and re-reviewed; remaining limitations; issue closure state.

    Please reconcile the board, unblock dependents, roll up parents, release my session, clean the safe completed worktree, recompute the current-phase eligible queue and refill every open implementation and review lane.

    Report once, stop editing and idle for release. Reviewer owns only the assigned issue/PR; the orchestrator owns shared project fields.

  6. Main orchestrator

    Reconcile board, release and clean up

    Project → Done

    Read back merge/issue state, record Done and clear the active owner. Refresh dependency eligibility and roll up completed parents. Release the settled reviewer. Preserve useful notes and remove only the completed worktree with no unique work. Recompute the current-phase eligible queue and refill every open implementation and review lane. Local main, origin/main and unresolved candidates are protected.

  7. Main orchestrator

    Refill lanes and continue the roadmap

    Parallel independent leaves · same phase

    Reconcile pending board writes, recompute dependencies and immediately fill open implementation or review lanes from the same phase's ascending eligible queue. Advance phase only when its required leaves are complete. Every scheduled check lists running tasks, tasks completed since the prior check, idle-lane reasons and verified progress percentages.

Only development completion

Bounded implementation + independent source review + reviewed integration.

No tests, database execution/review, hosted verification, screenshots, benchmarks, proof receipts or extra acceptance reviewer.

No Kestra orchestration, Testing deployment, promotion or Production delivery. Existing delivery hooks remain disabled.

Product permissions, tenant isolation, transactions, revisions and safe errors remain required functionality.

A blocker is not a new pickup

Investigate lack of useful progress at 15 minutes. At the estimate or 30-minute checkpoint, record remaining work and a revised estimate.

Resolve scope questions. On confirmed provider failure, preserve work, stop the old editor and reassign the same task. Let productive workers continue.

A real external approval or dependency block must be reported with its owner and resume condition. Do not skip order, bypass controls or retry unchanged denials.

The board follows events, not promises

EventRecord immediately
Worker startsIn progress; actual model, dispatch, branch and start time
Implementation handed offIn review; candidate commit; reviewer queued or active; implementer cleared
Blocked, failed or reassignedTruthful stage; exact blocker/resume condition; actual owner/model/estimate
Reviewer reports merged/closedOrchestrator writes Done; reviewed and merge commits; closed issue; no active owner; dependents refreshed
Partial API writeBoard-sync-pending; read current state and finish only missing writes before next pickup

At startup and every 15 minutes, reconcile workers, issue state, board owners and completion reports. Refresh the complete roadmap every 30 minutes or when it changes. Reviewer issue writes and orchestrator board writes have explicit, separate owners.
