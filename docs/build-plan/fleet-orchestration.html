Vortex · Fleet operating policy · 24 September 2026

One ready queue.
Several bounded tasks.

One orchestrator session of Opus 5.5 or GPT-6 Sol coordinates a parallel wave of dependency-ready work drawn from any phase. Independent workhorse agents build bounded leaves in separate worktrees. Opus 5.5 or GPT-6 Sol reviewers fix their own findings, re-review and close integrated work while the orchestrator keeps other eligible lanes moving.

This page explains the process. It is not a live status dashboard.

Cross-phase dispatch of dependency-ready leaves. Phase and Pickup Order are planning and reporting metadata, never dispatch gates. Keep eight independent implementer lanes filled by default, expanding to twelve when bounded non-overlapping work is eligible and provider capacity allows. Every handed-off candidate gets an independent reviewer in the same cycle, with up to six review-and-fix lanes spread across Opus 5.5 and GPT-6 Sol. Real dependencies, bounded scope, exclusive owning paths and capacity decide readiness; prefer lower Pickup Order only to break ties.

The issue lifecycle

  1. Main orchestrator · Opus 5.5 or GPT-6 Sol High

    Build the dependency-ready work wave

    Backlog → Ready

    Read the complete issue and comments, current spec, native dependencies and main source for each candidate. Identify what already exists and exactly what remains. Confirm outcome, owning paths, exclusions and code-review acceptance before assigning an agent.

    Readiness rules

    Read every roadmap page; ignore parent/phase rollups as dispatch targets. Scan every leaf across all phases and select dependency-ready leaves with non-overlapping ownership until the worker lanes are full. Phase and Pickup numbers do not control selection; prefer a lower Pickup Order only between equally ready leaves. Do not remove real blockers to manufacture readiness.

  2. Main orchestrator

    Shape the issue so nobody guesses scope

    Clear and bounded before dispatch

    Make sure the issue states its outcome, what is already built, numbered remaining work, owning paths and exclusions, acceptance criteria, and dependencies that match the native blockers. Rewrite anything missing, vague or contradicted by the source or specification, and record why in an issue comment. Send real product decisions to the user.

    When to split

    An issue is bounded when one implementer can finish it in one session: one outcome, one set of owning paths and no more than 180 active minutes. Split anything larger, or anything that mixes outcomes or owning paths, into sub-issues in the standard format, each with its own outcome, owning paths, acceptance and estimate. Give them a Pickup Order directly after the original without renumbering other issues, add native dependencies where order matters, and update the parent’s table and estimate total. If an implementer still reports unclear scope, fix the issue text as well as answering.

  3. Main orchestrator → workhorse fleet

    Assign bounded independent implementations

    Ready → In progress after actual start

    Read the full issue, comments, spec and current source first. Match complexity to model and current usage. Primary workhorses are GPT-6 Luna (Codex), OpenCode DeepSeek 4.1 Flash (deepseek/deepseek-flash), OpenCode GLM 5.3 Flash and Gemini 3.8 Flash Max or High, spread so no provider holds more than half the lanes when alternatives exist. Claude Sonnet 5 High is an alternative; do not select DeepSeek Pro. Reserve Opus 5.5 and GPT-6 Sol for review, orchestration and complex decisions. Record actual agent, estimate, branch, worktree, task and dispatch. Use one isolated issue worktree per leaf. Preserve drafts and unique work, and never duplicate a live or uncertain worker. A planned assignment or accepted input is not a started worker; the implementer sets its own row to In progress once its task really starts.

  4. Implementer → main orchestrator

    Build and hand off the candidate

    In progress → In review

    Commit and push the bounded change. Report functionality, candidate commit, acceptance mapping and limitations. Set its own row to In review and stop editing. The orchestrator settles/releases the implementer and gives a fresh reviewer exclusive ownership of the same worktree.

  5. Independent reviewer · Opus 5.5 or GPT-6 Sol High

    Read issue → review → fix → re-review

    In review

    Record itself as Current owner on its row, then first read the complete live GitHub issue, every comment and the linked specification. Then inspect the full candidate diff, current main and affected callers against functional acceptance. Fix findings directly, commit corrections and re-review the final source. Repeat inside this review session. Do not send ordinary fixes back to the implementer.

  6. Same reviewer

    Integrate, close and signal

    Reviewed source merged → issue completed

    Open the candidate PR if absent. Integrate the reviewed PR into main through permitted repository operations. Re-review conflict-resolution changes. Confirm merge, update the assigned issue with the implemented outcome and final review, and close it completed. Then set its own row to Done, clear Current owner and record the finish time. An open PR is not Done.

    Reviewer completion signal
    Issue / phase / pickup; PR; final reviewed commit; merge commit; functionality built; findings fixed and re-reviewed; remaining limitations; verified issue closure.

    Please verify these facts, reconcile the board, unblock dependents, roll up parents, release both settled agents, clean the safe completed worktree, recompute the eligible queue across phases and refill every open implementation and review lane.

    Send once through the supported Orca completion contract, stop editing and idle for release. The orchestrator verifies receipt and facts and reads back the Done row; the reviewer owns only the assigned issue, its PR and its own row, and the orchestrator owns every other shared project field.

  7. Main orchestrator

    Reconcile board, release and clean up

    Project → Done

    Read back merge/issue state and the reviewer’s Done row, and write any missing completion fields. Refresh dependency eligibility and roll up completed parents. Release both settled agents. Record cleanup pending, compare Orca and Git worktree inventories, then close idle terminals and remove the exact completed worktree only after confirming no live editor, unique commit, tracked or untracked work. Read both inventories back. Keep unsafe work with a named owner and next action. Board API delays do not delay independent safe cleanup. Recompute the eligible queue across phases and refill open lanes. Local main, origin/main and unresolved candidates are protected.

  8. Main orchestrator

    Refill lanes and continue the roadmap

    Parallel independent leaves · any phase

    Reconcile pending board writes, recompute dependencies and immediately fill open implementation or review lanes from any Ready non-overlapping leaf in any phase. Phase completion is a reporting rollup, not a dispatch gate. Every scheduled check lists running tasks, tasks completed since the prior check, idle-lane reasons and verified progress percentages.

Only development completion

Bounded implementation + independent source review + reviewed integration.

No tests or test edits, build/typecheck/lint gates, database execution/review, hosted verification, screenshots, benchmarks, proof receipts or extra acceptance reviewer.

No Kestra orchestration, Testing deployment, promotion or Production delivery. Existing delivery hooks remain disabled.

Product permissions, tenant isolation, transactions, revisions and safe errors remain required functionality.

A blocker does not idle Ready work

Investigate lack of useful progress at 15 minutes. At the estimate or 30-minute checkpoint, record remaining work and a revised estimate.

Resolve scope questions. A provider concurrency or capacity response is not a permission denial: retry the same terminal several times at about 20-second spacing. Only after repeated confirmed capacity failures preserve the work, stop the old editor and move the task to another workhorse or an offered fallback. Let productive workers continue.

A real external approval or dependency block must be reported with its owner and resume condition. Keep every other Ready leaf moving; do not bypass controls, change protections or retry unchanged denials.

The board follows events, not promises

EventRecord immediately
Worker startsImplementer writes In progress and start time; orchestrator records actual model, dispatch and branch
Implementation handed offImplementer writes In review; orchestrator records candidate commit, clears the implementer and starts the reviewer
Blocked, failed or reassignedTruthful stage; exact blocker/resume condition; actual owner/model/estimate
Reviewer reports merged/closedReviewer writes Done, finish time and no active owner; orchestrator reads it back, adds reviewed and merge commits and refreshes dependents
Partial API writeBoard-sync-pending; read current state and finish only missing writes before next pickup

At every start, handoff, merge and closure, reconcile workers, issue state and only the affected board rows. Journal desired changes, batch only fields that changed, read those rows back, and drain pending writes after the actual GraphQL reset. The coordinator shares one budgeted complete roadmap snapshot per reporting interval with the monitor, board audit and progress calculation. It pages through a slim Project inventory and fetches native relationships separately; it never nests large relationship lists beneath every Project row or repeats a full scan after a single field repair. Preserve at least one fifth of the hourly GraphQL budget for live Status and owner transitions. Count only reviewed, merged, closed and board-reconciled required leaves; atomically save overall and Phase 1–6 percentages with complete-snapshot and delta source times. If a source is unavailable, label the previous value STALE with the cause and next retry. Compare Orca and Git worktree inventories on completion and resume so completed workspaces cannot accumulate unnoticed. Each worker writes only its own issue’s row at its own transitions; the orchestrator owns every other shared board write.
