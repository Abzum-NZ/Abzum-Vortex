# Vortex contracts

[Platform specification](../docs/specification/README.md) | [Data-contract appendix](../docs/specification/appendices/data-contracts.md) | [Build plan](../docs/build-plan/README.md#phases) | [Validation-error author guide](VALIDATION_ERRORS.md)

This package defines shared Zod contracts and inferred TypeScript types for authored definition documents, compilation and publication, runtime data and operations, and platform catalogues. The authored-source contracts for modules, applications, and connection types are separate from canonical runtime contracts: authors use readable aliases, while published definitions use immutable platform-issued identifiers.

The package root, `@vortex/contracts`, resolves to `src/index.ts`. The package also exposes `@vortex/contracts/shadcn-theme-releases` from `src/shadcn-theme-releases.ts` as a separate subpath. Contract modules use Zod, semver, package-local contracts, and catalogue assets; they do not import browser, server, database, Supabase, Kestra, or service implementations.

The authored-source object schemas reject unknown properties, while fields explicitly typed as opaque JSON accept the values allowed by `jsonValueSchema`. Other schemas describe their own explicit contract shapes. A successful parse validates shape and any represented evidence; it does not authenticate a caller, decide permissions, approve a grant, read protected current state, commit a transaction, or perform an operation.

Reference inspection follows declared schemas through `walkDefinitionContract`, not arbitrary property names. Opaque JSON uses `jsonValueSchema`; its contents are validated, but the reference walker treats the value as a leaf. Fingerprints cover definition content without treating user-defined record-map keys as references. Publication and version comparison share `unresolvedRecordTypeReferencePaths`, and genuine unresolved references still fail. See [#258](https://github.com/Abzum-NZ/Abzum-Vortex/issues/258) and [Zod's schema traversal documentation](https://zod.dev/packages/core#internals).

## Authority boundaries

Parsing a contract does not authenticate the actor, make an access decision, approve a grant, read protected current state, or commit a change. Protected callers and storage paths apply those checks. In particular, an eligible assignment permits a person to request activation but grants no role permissions by itself; privileged activation is a separate, time-limited Access fact for one organisation account.

Assignment-change commands describe grant or revoke requests against current assignment facts. Their results describe the stored assignment and resulting Access version, not effective permission. Role-change candidates separate local role edits from explicit permission acceptance and bind the proposed operation to any required affected-assignment review evidence. Parsing or preparing a candidate does not read current authority or grant access.
